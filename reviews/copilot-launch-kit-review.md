# GitCheck launch-kit review

## Overall verdict: **DO NOT LAUNCH**

The kit is a useful product outline, but its rules engine would misclassify a common SPDX license (`BSL-1.0`), and its planned scan cannot reliably build a resolved dependency tree from the listed manifests alone. The all-client-side API plan and the final-window launch dependencies also remain insufficiently verified. Fix the license rules, narrow the first shippable slice, and make live/demo and failure states explicit before treating this as an approval-ready launch plan.

This is a review of the kit, not legal advice. The kit's own disclaimer is appropriate and should remain verbatim in the app footer and every exported report (§ intro, §5 prompt 1).

## 1. SPDX rules correctness — **FAIL**

**Evidence and findings**

- **Wrong SPDX/license-family classification:** §2 calls `BSL-1.0` source-available/non-OSI (§2, line 37). `BSL-1.0` is the **Boost Software License 1.0**, an OSI-approved permissive license. The unrelated Business Source License uses `BUSL-1.1` as its SPDX identifier. This would generate a false high-risk finding for ordinary Boost-licensed dependencies. Sources: [SPDX BSL-1.0](https://spdx.org/licenses/BSL-1.0.html), [SPDX BUSL-1.1](https://spdx.org/licenses/BUSL-1.1.html).
- **GPL version and `-or-later` rules need directionality:** §2 correctly flags Apache-2.0 combined with GPL-2.0-only and recognizes that GPL-2.0-or-later can permit GPL-3.0 terms (§2, lines 41, 43). But “`-or-later` resolves it” is too broad: GPL-3.0-or-later does not permit choosing GPL-2.0-only. Parse each license expression, including `WITH` exceptions, and evaluate the actual permitted choice rather than comparing major-version labels alone. Apache-2.0/GPL-2.0-only is a sound incompatibility warning for a combined work; it should not imply every mere dependency relationship is necessarily a combined work.
- **Weak-copyleft rules collapse important distinctions:** §2 combines LGPL, MPL, EPL, and CDDL and assigns broad outcomes (§2, lines 34, 42). LGPL obligations depend on modifications and linking; static linking has relinkability/source obligations too, so “dynamic linking / relinkability” is incomplete. MPL-2.0's source obligations are file-level and attach to covered files, not generically to a whole application. EPL-1.0 and CDDL-1.0 have GPL incompatibility concerns for combined works; EPL-2.0 has a conditional secondary-license mechanism, so an unconditional EPL/CDDL-to-GPL rule misses a material case. See [GNU license compatibility](https://www.gnu.org/licenses/license-compatibility.html), [Eclipse EPL-2.0 FAQ](https://www.eclipse.org/legal/epl-2.0/faq/), and [Mozilla MPL-2.0 FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/).
- **AGPL trigger is overgeneralized:** §2 says an AGPL dependency is High for any project other than AGPL-3.0 and describes the obligation as “network-use source disclosure” (§2, line 44). AGPLv3 §13 is not a generic obligation for every network use of an AGPL dependency: it concerns a modified version of the AGPL program that users interact with remotely and offering those users its corresponding source. The result depends on what is modified, combined, and conveyed. The UI should describe a potential obligation and the relevant condition, not assert an automatic conflict. Source: [GNU AGPLv3, section 13](https://www.gnu.org/licenses/agpl-3.0.html).
- **SPDX expression semantics are oversimplified:** §2 says `OR` means evaluate the most permissive option and `AND` means evaluate the stricter one (§2, line 47). `OR` permits a choice only when that choice is actually available and selected; `AND` means both licenses' terms apply, not that one can always be represented by whichever option the engine calls “stricter.” Grouping and `WITH` exceptions must also be parsed. If the app cannot resolve an expression, return Unknown rather than silently selecting a license.
- **Other edge cases:** §2 treats CC0-1.0 as an ordinary software-permissive license and broadly labels every “NonCommercial” identifier source-available (§2, lines 33, 37). CC0 is a public-domain dedication/waiver, not a standard software license; preserve its distinct label and avoid implying every Creative Commons license is a software license. `Commons-Clause variants` is not a single SPDX family identifier; unrecognized license text should remain Unknown until matched to a verified identifier. §2's `NOASSERTION`, `LicenseRef-*`, and empty-as-Unknown rule is a good conservative baseline (§2, lines 38, 46).
- **No-license handling is appropriately cautious but needs conditional wording:** §2 correctly treats no license as a risk and §1 says no license means the owner has not granted general reuse permission (§1, line 21; §2, line 48). A project without a license does not by itself establish that a separately used dependency is part of a derivative work; present the combined-work assessment as unverified rather than as a categorical legal conclusion.
- **Disclaimer:** The required “not legal advice” text is specified verbatim for the app footer and reports (§ intro, line 13; §5, line 84), and README repeats it. Keep it in both live and Demo Mode screens and in each export.

**Paste-ready replacement rule for §2's family/rule entries**

> **Source-available identifiers:** classify `BUSL-1.1`, `SSPL-1.0`, `Elastic-2.0`, and verified non-commercial/custom terms as source-available/restricted, not OSI-approved open source. `BSL-1.0` is Boost Software License 1.0 and belongs in Permissive. Treat unrecognized `LicenseRef-*`, unparsed expressions, and license text not matched to a verified SPDX identifier as Unknown.
>
> **Evaluate context, not license names alone:** parse SPDX `OR`, `AND`, and `WITH` expressions; report the chosen `OR` option only when the user or source establishes it, and do not reduce `AND` to a single “stricter” license. Assess compatibility only for dependencies that may be combined or distributed with the project; otherwise report the relationship as conditional/unknown. GPL `-or-later` permits choosing that version or a later GPL version, never an earlier one. For LGPL, explain library modifications and linking/relinking conditions; for MPL-2.0, identify covered files; for EPL, distinguish EPL-1.0 from EPL-2.0 and verify the secondary-license option; for CDDL, flag same-work GPL incompatibility as conditional. For AGPL-3.0, flag a potential §13 obligation only when a modified AGPL program is offered for remote interaction, and explain that users must be offered its corresponding source.

This is intentionally conservative, general-purpose product guidance, not a substitute for legal review of a specific distribution.

## 2. API feasibility in a client-side React app — **NOT VERIFIED**

The named API families and most endpoint shapes are plausible, but §3's blanket “all ... called client-side” plan (§3, lines 54–61) is not established by the kit or the documentation reviewed here for every endpoint, origin, and response. In particular, verify browser CORS and unauthenticated quotas for deps.dev and both registry fallbacks from the deployed Bolt origin before relying on them. “If a host blocks a call” (§3, line 61) is not a substitute for confirming that the calls work.

- **GitHub:** The repo, license, contents, and tree endpoints exist; GitHub documents CORS support and a 60-requests/hour unauthenticated REST limit. A recursive tree is not an unlimited paginated file list: inspect its `truncated` flag and stop with a partial/incomplete result rather than silently missing manifests. The Contents API is limited to 1,000 entries per directory. A token entered into a browser is visible to the user and exposed to page scripts; “stored only in memory” does not make it secret (§3, line 56). Use least privilege, never persist it, and offer a no-token path. Sources: [GitHub CORS](https://docs.github.com/en/rest/using-the-rest-api/using-cors-and-jsonp-to-make-cross-origin-requests), [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [Contents API](https://docs.github.com/en/rest/repos/contents), [Git Trees API](https://docs.github.com/en/rest/git/trees).
- **GitLab:** The project, repository tree, and repository files/raw endpoints exist (§3, line 57). URL-encode the complete subgroup/project path as the project ID segment, and separately encode file paths and refs where required. Follow the endpoint's returned pagination information; do not assume a recursive request returns the entire tree. The tree API supports recursion and is paginated. Confirm unauthenticated browser CORS and live limits against GitLab.com. Sources: [GitLab REST API](https://docs.gitlab.com/api/rest/), [repository tree](https://docs.gitlab.com/api/repositories/), [repository files](https://docs.gitlab.com/api/repository_files/).
- **Bitbucket:** `/2.0/repositories/{workspace}/{repo}` and `/src/{ref}/{path}` are valid API patterns (§3, line 58). Source listings are paginated; follow the returned `next` URL and bound the number of pages/files. Encode branch/ref and path segments safely. Confirm the chosen endpoints' unauthenticated CORS behavior and rate limits from the app origin. Sources: [Bitbucket source endpoint](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-source/), [pagination](https://developer.atlassian.com/cloud/bitbucket/rest/intro/#pagination).
- **deps.dev:** `GetVersion` and `GetDependencies` are documented API operations, and the `:dependencies` REST suffix in §3 is consistent with its API pattern (§3, line 59). However, the plan must verify the exact system identifiers, package/version path encoding, CORS, quotas, and which graph depth the endpoint returns; do not treat one response as a complete transitive graph without confirming its response semantics. Source: [deps.dev API reference](https://docs.deps.dev/api/v3/). Maven `group:artifact` and scoped npm names need encoding as one package-name path segment and tests against real requests.
- **Registry fallbacks:** npm's package metadata and PyPI's version JSON are real endpoints (§3, line 60), but PyPI `info.license` and classifiers can be free text or absent, not a dependable SPDX expression. Preserve the source string; map only recognized values and otherwise return Unknown. Check CORS, requested versions, and anonymous quotas. For scoped npm packages, test the exact encoded URL.
- **Version and size constraints:** §1 proposes `GetVersion`/`GetDependencies` calls per dependency but lists manifests, not lockfiles (§1, lines 22–23). Manifest ranges such as `^1.2`, `>=...`, or unpinned requirements are not resolved versions. The version-specific deps.dev calls therefore cannot reliably identify the selected dependency graph without lockfiles or a clear unresolved state. Tree limits and pagination also make “scan all files” unsafe for large repositories (§1, line 22; §3, lines 56–58).

**Paste-ready replacement for §3's CORS/behavior note**

> Before enabling each live host, test its exact API calls in a browser from the deployed origin, including CORS, unauthenticated access, pagination, rate-limit responses, and encoded paths. Bound pages, files, response sizes, and dependency nodes. If a live request fails or a tree is truncated, show the live scan as failed/incomplete with the exact reason; never substitute bundled Demo Mode data into a live result. Only show a Demo result after the user explicitly selects Demo Mode.

Until those runtime checks pass, label cross-host client-side scanning as **NOT VERIFIED**, not as a launch-ready capability.

## 3. Starter prompt quality — **FAIL**

- **Prompt 1 is over-scoped for a six-hour first window:** §5 asks for multi-host URL detection, three demos, full results UI, graph/tree interaction, risk ranking, detail drawer, table, both exports, an SPDX expression rules engine, and full disclaimers in one build (§5, lines 76–86). The described scan also implies dependency resolution, while §5 simultaneously says live fetching can be added later. There is no acceptance checklist or explicit boundary between a demo-only core and a live scan. On GLM 5.3 Flash, this is a high rewrite/debug risk, not a bounded first deliverable.
- **Resolution work is pushed too late and is too wide:** Window 2 covers GitHub plus many parsers; Window 3 then adds resolution across seven ecosystems and both fallbacks; Window 4 adds two hosts and real-repo tests (§6, lines 91–93). Those steps depend on one another, but there is no checkpoint that keeps each window's result buildable and demoable. Window 7 is the first explicit parser/edge-case test pass, after all new features (§6, lines 96–97).
- **Prompt 1 and §2 disagree on the rule set:** §2 includes MIT-0, ISC, BSD-3-Clause, EPL-2.0, EUPL, CDDL, LGPL variants, and several other cases (§2, lines 33–38); Prompt 1's abbreviated families omit some of these (§5, line 83). It also repeats oversimplified EPL/GPL and AGPL rules. A generated engine could ship behavior that contradicts the product spec.
- **“Keep ... modules ... so live fetching can be added without rewriting the UI” is directionally good** (§5, line 86), but it is not an acceptance test. Require a stable scan/result type and tests before later prompts extend those modules.

**Paste-ready Prompt 1 scope**

> Build a working offline-first GitCheck core for this window. Deliver: (1) the URL-entry shell with explicit Live Scan and Demo Mode actions; (2) three bundled, clearly labeled, fully offline sample results; (3) a typed scan/result model and a small, separately tested SPDX rules module; (4) the results table, risk list, and Markdown/JSON export from that same result model; and (5) loading, empty, error, and unknown-license states. Do not implement live APIs, all manifest parsers, or a force-directed graph in this window. Keep each area in a separate module so later prompts extend it without replacing working behavior. Finish by running the existing checks, manually exercising all three demos offline, and listing any incomplete items.

For subsequent prompts, add one integration at a time, require a working build and regression check at the end of each window, and do not add a new feature if that window's acceptance checks fail.

## 4. Spec completeness and demo honesty — **FAIL**

- **Missing specified outcomes:** §1 defines the happy path, but does not prescribe user-visible outcomes for malformed/unsupported URLs, private or inaccessible repositories, host `404`/`403`, no manifest, unsupported manifest, parser failure, truncated tree, or partial scan (§1, lines 19–28). Window 2 mentions private/not-found/rate-limited errors and Window 8 says “empty/error states,” but these are late, terse tasks (§6, lines 91, 97). A public unauthenticated API often cannot distinguish a private repository from a nonexistent one; report “not found or inaccessible” unless authentication proves the distinction.
- **No lockfile or exact-version plan:** §1's manifest list covers manifest files but not package lockfiles or a policy for dependency ranges (§1, lines 22–23). Without resolved versions, version-specific metadata and transitive edges cannot be claimed as a complete live dependency chain. Mark range-only dependencies unresolved or explicitly limit the first live scan to supported lockfiles.
- **Monorepos are ambiguous:** §1 says to look for manifests but gives no package-root selection, multiple-manifest grouping, or cross-workspace deduplication behavior (§1, lines 22–23). Window 7 defers monorepo handling to the final test window (§6, line 96). Do not combine unrelated packages into one verdict; either scan each manifest root separately or ask the user to select one.
- **Unknown and no-license cases are partly covered:** §1 explicitly flags a missing project license, and §2 correctly makes unknown dependency licenses a separate risk (§1, line 21; §2, line 46). But there is no defined result when the project's own license cannot be mapped, when no manifest is found, or when a manifest parses but dependency versions cannot be resolved.
- **Demo/live separation has a direct ambiguity:** §8 correctly says never present Demo Mode as a live scan, and §5 requires offline samples (§5, line 81; §8, line 112). But §3 says a blocked live request should “fall back to Demo Mode data” (§3, line 61). Unless the interface requires a fresh explicit mode selection and prominently labels every demo result, this can turn a live scan into a misleading demo result. A demo is a separate user-selected action, not an automatic fallback.
- **Honesty is also affected by progressive completeness:** §1 sets caps of depth 3 and 250 nodes (§1, line 23); results must show the cap/partial state and must not imply that an incomplete graph represents every dependency. The same applies to unrecognized license text and parser omissions.

**Paste-ready empty/error and mode rule**

> Every result displays its source: **Live scan** or **Demo Mode — bundled sample, not a live scan**. Demo Mode is entered only by an explicit user action and works without network access; live failures never auto-load a sample. For live scans, show distinct states for invalid/unsupported URL, not found or inaccessible (including private without authorization), rate limited, network/CORS failure, no LICENSE, no manifest, unsupported/unparseable manifest, unresolved version, truncated/over-limit tree, and partial dependency graph. Preserve unknown license text as Unknown. Never show a complete/compatible verdict when required files, versions, or graph nodes were unavailable.

## 5. Weekend plan and ship risk — **FAIL**

There are eight six-hour windows as stated, but §6 allocates the final Window 8 to “Final polish, empty/error states, accessibility pass, publish” (§6, lines 89–97). The intro also makes linking to GitHub a launch requirement (§intro, line 4), while §intro and §6 defer domain setup/publishing to the last window (§intro, lines 5, 10; §6, line 97). DNS propagation, host verification, HTTPS certificate provisioning, and a successful GitHub round trip have external dependencies and no guaranteed completion time. Bolt's current docs direct users to connect the domain in Bolt and use the DNS records Bolt supplies; they do not verify the kit's specific root ALIAS and `site-dns.bolt.host` values. Source: [Bolt domain connection guide](https://support.bolt.new/cloud/domains/connect). Do not treat a DNS recipe copied from another site as a verified Bolt requirement.

### Five largest ship risks, ranked, with smallest pre-launch mitigation

1. **Incorrect license verdicts (critical).** `BSL-1.0` is assigned to the wrong family, while expression, EPL, and AGPL rules are too categorical (§2, lines 37, 42–47). **Before launch:** correct the identifier to Boost/permissive; distinguish `BUSL-1.1`; paste in the conditional expression/AGPL/EPL rule above; add a tiny table of known cases: Apache-2.0 + GPL-2.0-only, GPL-2.0-or-later + GPL-3.0-only, GPL-3.0-or-later + GPL-2.0-only, LGPL static linking, MPL file changes, and EPL-2.0 secondary-license absent/present.
2. **Live scanning produces an incomplete or fabricated chain.** No lockfiles or range-resolution policy are specified; the three-host APIs have pagination/size limits and CORS/quota behavior not fully verified (§1, lines 22–23; §3, lines 56–61). **Before launch:** explicitly limit the first live slice to one host and supported lockfiles; mark everything else unsupported/unresolved; smoke-test one small public repository in the deployed browser and verify partial/error reporting.
3. **First-window scope consumes the build budget.** Prompt 1 combines architecture, the rules engine, results UI, exports, three demos, and broad scanning goals (§5, lines 76–86). **Before launch:** replace it with the scoped Prompt 1 above and define “done” as an offline build with all three demos and exports working. Defer graph view and broad parser coverage.
4. **The final window cannot absorb feature work and launch operations.** The kit reserves Window 8 for polish plus publish, while domain setup and GitHub integration are launch requirements (§intro, lines 4–5; §6, line 97). **Before launch:** connect and verify Bolt↔GitHub in Window 1; create the first deploy as soon as the offline core builds; follow Bolt's domain-specific DNS instructions and start DNS/TLS verification before Window 8. Set a hard fallback: if `gitcheck.tech` is not verified by Sun 6pm PT, publish and announce the working Bolt URL rather than risk the final launch.
5. **The schedule depends on unconfirmed promotion terms and human setup.** §8 explicitly says the free-weekend/6-hour reset terms could not be confirmed publicly (§8, line 109); account access, domain records, and model usage are external to the build. **Before launch:** verify the Forge banner/credit meter before spending credits, write down the actual reset times, confirm access to the Porkbun/Bolt/GitHub accounts, and prepare a reduced-scope fallback that is Demo Mode only. Treat the stated promotion as unverified until the account itself confirms it.

**Small scheduling fix for §6 Window 8**

> Window 8 (Sun 6–11:59pm PT) — Release gate only: run the already-defined smoke checks, verify the published URL and GitHub sync, and fix only ship-blocking defects. Do not add features or begin DNS setup in this window. If the custom domain is not already verified by Sun 6pm PT, publish on the working Bolt URL and defer the custom-domain cutover.
